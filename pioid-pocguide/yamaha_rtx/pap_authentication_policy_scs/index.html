    SCS評価制度におけるリモートアクセスVPN認証強化の考え方

    文書更新日: 2026-05-16

    参照資料: IPA「SCS評価制度 ★3・★4 要求事項・評価基準」（2026-05-16参照）

    本書は、YAMAHA RTX のリモートアクセスVPNで PIO-ID のクラウドRADIUSを利用する場合に、SCS評価制度の観点でどのように説明できるかを整理した文書です。

    SCS評価制度への適合を単独で保証するものではありませんが、リモートアクセスVPNの認証強化を説明する際の判断材料として利用することを目的としています。

    結論

    YAMAHA RTX と PIO-ID を組み合わせたリモートアクセスVPNの2要素認証は、SCS評価制度における認証強度、多要素認証、パスワード設定ルール、ネットワーク境界防護の考え方に沿った対策として説明できます。

    SCS評価制度の公開要求事項では、現時点でリモートアクセスVPNそのものを名指しした要求は確認できません。ただし、★4では「インターネットを経由して社内環境へ接続する場合」に多要素認証を使用する要求が示されており、リモートアクセスVPNを説明しやすい項目になっています。

    本構成では、パスワードに加えてワンタイムパスワード（OTP）を利用します。これにより、静的パスワードのみを利用するVPN認証と比較して、パスワード漏えい、使い回し、リスト型攻撃に対するリスクを低減できます。

    SCS評価制度との関係

    本書では、IPAが公開している「SCS評価制度 ★3・★4 要求事項・評価基準」（2026-05-16参照）のうち、YAMAHA RTX のリモートアクセスVPN認証と関係する項目を整理します。

    SCS評価制度の公開要求事項では、現時点でリモートアクセスVPNそのものを名指しした要求は確認できません。ただし、認証の強度、多要素認証、パスワード設定ルール、ネットワーク境界防護、ログ取得に関する項目は、リモートアクセスVPNの認証方式を評価する際の判断材料になります。

    本構成は、SCS評価制度への適合を単独で保証するものではありません。SCS評価制度では、認証方式だけでなく、資産管理、ログ管理、ネットワーク境界防護、運用ルールなども含めて評価されます。そのため、本構成は「SCS評価制度の認証強度や多要素認証の考え方に沿った対策」として位置づけるのが適切です。

    関連する要求事項とコメント

    項目 レベル 要求事項の要点 RTXのローカル認証のみの場合 PIO-IDを併用する場合の説明
    4-1-1-1 ★3 ユーザIDの付与・変更・削除を申請・承認制にすること。 VPNユーザをRTXのローカル設定で個別に管理するため、申請・承認の記録や他システムとの整合を別途管理する必要があります。 PIO-ID側でユーザを管理することで、VPN利用者の追加・変更・削除をID管理の運用に寄せやすくなります。
    4-1-1-2 ★3 ユーザIDを共有しないこと。共有が必要な場合は利用者を特定できるようにすること。 共有VPNアカウントで運用すると、誰が接続したかを特定しにくくなります。 ユーザごとのPIO-IDアカウントでVPN認証することで、共有IDを避け、利用者単位の認証として説明できます。
    4-1-1-3 ★3 不要になったユーザIDを速やかに削除または無効化すること。 RTXのローカル認証DBに残ったVPNユーザの削除漏れが発生しやすくなります。 PIO-ID側でユーザを無効化・削除することで、VPN利用権限も合わせて停止しやすくなります。
    4-1-1-4 ★3 不要になったアクセス権を速やかに削除または無効化すること。 拠点や機器ごとにVPNユーザを管理している場合、権限変更時の反映漏れが起きやすくなります。 PIO-IDのグループや認証ルールを使うことで、VPNアクセス権の変更を集中管理しやすくなります。
    4-1-2-1 ★3 すべてのサーバおよびネットワーク機器について、システム管理者および責任者を定めること。 RTXを管理する責任者を機器ごとに明確にする必要があります。 PIO-IDは責任者の指定そのものを代替するものではありませんが、管理者ログインをユーザ単位にすることで、責任者・管理者の整理をしやすくなります。
    4-1-2-2 ★3 管理者IDを共有しないこと。共有が必要な場合は利用者を特定できるようにすること。 RTX管理者アカウントを共有すると、管理操作を行った個人を特定しにくくなります。 RTXの管理者ログインもPIO-IDで認証する構成にすれば、管理者ごとの認証として説明しやすくなります。
    4-1-2-3 ★3 管理者IDには用途に応じた必要最低限の権限のみを付与すること。 RTX本体側だけで管理者権限を運用する場合、管理対象者の棚卸や権限管理を別途行う必要があります。 PIO-ID側のユーザ・グループ管理と組み合わせることで、管理者を限定する運用に寄せやすくなります。
    4-1-2-5 ★3 誰が管理者IDを持っているかを把握する仕組みを整備すること。 機器ごとのローカル管理では、管理者の一覧化や棚卸が煩雑になります。 PIO-IDに管理者認証を集約することで、管理者IDの把握と棚卸を行いやすくなります。
    4-1-2-6 ★3 不要になった管理者IDを速やかに削除または無効化すること。 RTX側に管理者アカウントが残ると、退職・異動後の削除漏れがリスクになります。 PIO-ID側で管理者を無効化・削除することで、管理アクセスの停止を集中管理しやすくなります。
    4-1-2-7 ★3 管理者IDの付与・変更・削除を申請・承認制にすること。 機器ごとに手動で管理する場合、申請・承認と実設定の対応を別途確認する必要があります。 PIO-ID側の管理プロセスに寄せることで、管理者IDの付与・変更・削除を統制しやすくなります。
    4-1-2-8 ★3 管理者IDの付与・変更・削除やネットワーク機器の設定変更を行う権限を、業務上必要な者に限定すること。 RTXの設定変更権限をローカル管理だけで運用すると、対象者の限定や棚卸を別途行う必要があります。 管理者ログインをPIO-ID認証に寄せることで、設定変更できる管理者をユーザ・グループ単位で整理しやすくなります。
    4-1-3-1 ★3 アクセス許可前に、ユーザIDごとの認証情報でユーザを認証すること。 ローカル認証DBでも実現できますが、共有IDや削除漏れがあるとユーザ単位の認証として弱くなります。 ユーザごとのPIO-IDアカウントでVPN認証することで、利用者単位の認証として説明できます。
    4-1-3-3 ★3 多要素認証では、知識情報、所有情報、生体情報、その他の情報から2種類以上を利用すること。 RTXのローカルパスワード認証のみでは、知識情報だけの認証になります。 パスワードを知識情報、OTPを所有情報として扱うことで、多要素認証として説明できます。
    4-1-3-4 ★3 多要素認証の知識情報として用いるパスワードは8文字以上とすること。 RTX側だけでパスワードルールを組織全体に合わせて維持するには、別途運用管理が必要です。 PIO-ID側のパスワードポリシーを利用し、VPN利用者にも同じ方針を適用しやすくなります。
    4-1-3-5 ★4 インターネット経由で社内環境へ接続する場合などは、多要素認証を使用すること。 リモートアクセスVPNが静的パスワードのみの場合、この考え方に対する説明が弱くなります。 VPN接続にOTPを追加することで、インターネット経由の社内接続に多要素認証を適用する対策として説明できます。
    4-1-5-1 ★3 デフォルトパスワードを変更するルールを定めること。 RTXの初期管理パスワードやローカルユーザの初期設定を個別に管理する必要があります。 PIO-ID認証へ寄せる場合でも、RTX本体の管理パスワード変更は別途必要です。PIO-IDは利用者認証・管理者認証の集中管理を補完します。
    4-1-5-2 ★3 推測されやすい単語のパスワード設定を禁止すること。 RTX側のローカルパスワードだけで組織のパスワードポリシーを徹底するには、運用確認が必要です。 PIO-ID側のパスワードポリシーに寄せることで、VPN認証にも推測されにくいパスワード運用を適用しやすくなります。
    4-1-5-3 ★3 パスワード認証では、多要素認証または試行回数制限を組み合わせたうえで8文字以上とすること。 静的パスワードのみのVPN認証では、多要素認証の説明ができません。 PIO-IDのOTPを追加することで、パスワード認証に多要素認証を組み合わせる構成として説明できます。
    4-1-5-4 ★3 情報機器およびサービス間でパスワードを使い回さないようにすること。 VPN専用のローカルパスワードをユーザが個別に管理するため、使い回しの確認が難しくなります。 PIO-ID側のID管理・パスワードポリシーに寄せることで、利用者ごとのパスワード管理を統制しやすくなります。
    4-1-5-5 ★3 パスワード設定ルールを利用者に周知すること。 VPNだけ別ルールになると、利用者への周知や運用が分散しやすくなります。 PIO-IDの利用ルールとして、VPN認証を含めたパスワード・OTP利用方針を周知しやすくなります。
    4-1-6-1 ★3 パスワードを安全に保管するルールを定めること。 VPN専用パスワードを端末やメモに保存する運用になりやすく、管理が分散します。 PIO-IDの認証に寄せることで、VPN専用のローカルパスワード管理を減らし、OTP併用で漏えい時のリスクも下げられます。
    4-1-6-2 ★3 パスワード漏えい時、速やかに変更する手順を定めること。 RTXローカル認証では、機器ごとに該当ユーザのパスワード変更や無効化が必要になります。 PIO-ID側でパスワード変更、ユーザ無効化、OTP再設定などを集中して行いやすくなります。
    4-1-6-3 ★3 パスワード管理ルールを利用者に周知すること。 VPN専用の例外運用があると、周知内容が複雑になります。 PIO-IDの利用ルールにVPN認証を含めることで、認証ルールの周知を一本化しやすくなります。
    4-1-7-1 ★3 アクセス権の発行・変更・削除、範囲限定、棚卸、台帳管理のルールを定めること。 RTXごとのローカル認証では、VPNアクセス権の台帳管理や棚卸を別途行う必要があります。 PIO-IDのユーザ・グループでVPN利用可否を管理することで、アクセス権の発行・変更・削除を整理しやすくなります。
    4-1-7-2 ★4 年1回以上、付与したアクセス権の棚卸を実施すること。 RTXに登録されたローカルユーザを機器ごとに確認する必要があります。 PIO-ID側のグループやユーザ一覧を基準に、VPNアクセス権の棚卸を行いやすくなります。
    4-1-7-3 ★4 重要な機密情報を扱うシステムは、アクセス権付与の条件を定めること。 VPN接続後に重要システムへ到達できる場合、VPN利用条件を別途明確にする必要があります。 PIO-IDのグループ条件を用いて、VPN利用を許可する対象者を定義しやすくなります。
    4-1-7-4 ★4 重要な機密情報を扱うシステムのアクセス権設定について、システム管理者の要件および設定手順を定めること。 VPN接続が重要システムへの入口になる場合、誰がVPNアクセス権を設定するか、どの手順で設定するかを明確にする必要があります。 PIO-ID側のユーザ・グループ設定手順とRTX側のVPN設定手順を分けて整理し、運用手順として明文化しやすくなります。
    4-1-7-5 ★4 ユーザおよび管理者ごとに必要最小限の権限を付与すること。 共有VPNアカウントや広いアクセス許可では、最小権限の説明が難しくなります。 ユーザ・グループ単位でVPN利用可否や管理アクセス可否を分けることで、最小権限の考え方に寄せやすくなります。
    4-1-7-6 ★4 付与したアクセス権の運用・利用状況を監視する仕組みを整備すること。 RTX側の接続ログだけでは、利用者管理や認証失敗状況の確認が分散しやすくなります。 PIO-IDの認証ログとRTX側のVPN接続ログを組み合わせることで、VPN利用状況を確認しやすくなります。
    4-5-1-3 ★3 ファイアウォールまたはルータの認証は、パスワード設定等に関する評価基準を満たすこと。 RTXはルータであり、VPN利用者や管理者の認証も評価時の確認対象になり得ます。 VPN利用者認証や管理者ログインをPIO-IDに寄せることで、パスワードポリシーやOTPの適用を説明しやすくなります。
    4-5-1-4 ★3 認証されていないインバウンド通信を遮断すること。 VPN公開ポートはインターネット側の入口になるため、認証前通信と認証後通信の扱いをRTX側で適切に設計する必要があります。 PIO-IDは認証強化を担います。境界防護そのものはRTX側のVPN設定、ファイアウォール設定と合わせて確認します。
    4-5-1-7 ★3 インターネット経由でファイアウォール・ルールを変更する場合は、多要素認証または信頼できるIPアドレス制限を適用すること。 RTXの管理画面をインターネット経由で利用する場合、ローカルパスワードのみでは説明が弱くなります。 RTXの管理者ログインもPIO-IDで認証する構成にすれば、管理アクセスへの多要素認証として説明できます。
    4-4-3-1 ★4 ファイアウォール、プロキシサーバ、認証サーバなどのログを取得・保管すること。 RTX側のVPNログだけでは、認証サーバ側の成功・失敗やユーザID単位の確認が不足する場合があります。 PIO-IDの認証ログとRTX側のVPN接続ログを組み合わせることで、認証結果と接続状況を確認しやすくなります。保存期間や取得項目は別途確認が必要です。

    Note

    4-1-3-2は、重要な機密情報を取り扱うクラウドサービスへのアクセスを対象とした項目です。本書ではリモートアクセスVPN認証の説明資料として扱うため、関連項目には含めていません。

    SCS評価制度の観点での説明例

    YAMAHA RTX と PIO-ID を組み合わせたリモートアクセスVPNの2要素認証は、SCS評価制度における認証強度、多要素認証、パスワード設定ルール、ネットワーク境界防護の考え方に沿った対策として説明できます。

    特に、リモートアクセスVPNはインターネット経由で社内環境へ接続する入口になるため、静的パスワードのみで認証するのではなく、パスワードとOTPを組み合わせることにより、認証強度を高めることができます。

    一方で、SCS評価制度は認証方式だけで評価されるものではありません。SCS評価制度の観点で説明する場合は、以下も合わせて確認してください。

    • PIO-ID側のパスワードポリシー
    • OTPの利用対象ユーザ
    • YAMAHA RTX側のVPN設定と管理アクセス設定
    • RADIUS共有シークレットの強度
    • VPN装置とRADIUSサーバ間の通信経路制限
    • 認証ログおよびVPN接続ログの取得・保管
    • 管理者IDの管理手順

    ローカル認証DBとの比較

    YAMAHA RTX のローカル認証DBで静的パスワードのみを利用する場合、RADIUS通信によるパスワード送信は発生しません。

    一方で、静的パスワードのみの認証では、次のリスクが残ります。

    • パスワードの使い回し
    • 漏えい済みパスワードを使ったリスト型攻撃
    • 弱いパスワードに対する総当たり攻撃
    • 退職者や異動者のアカウント管理漏れ
    • 拠点や機器ごとの認証情報管理のばらつき

    PIO-ID のクラウドRADIUSを利用した2要素認証では、パスワードに加えてOTPを要求できます。そのため、パスワードが漏えいした場合でも、それだけでVPN接続が成立しにくくなります。

    この点で、VPN全体の認証リスクを比較して判断することが重要です。

    判断時のポイント

    SCS評価制度の観点で確認する場合は、次の観点で整理すると判断しやすくなります。

    • 認証情報がそのまま平文で送信されていないこと
    • VPN通信が暗号化されていること
    • RADIUS共有シークレットが十分に強固であること
    • パスワードのみではなくOTPを組み合わせていること
    • 管理者が利用者の追加、削除、無効化を適切に管理できること
    • 認証ログを確認できること
    • VPN装置やRADIUS設定の変更権限が適切に管理されていること

    認証情報の保護に関する補足

    SCS評価制度の観点では、多要素認証の有無、パスワードポリシー、ログ取得、ネットワーク境界防護を中心に整理するのが適切です。

    一方で、社内確認の過程で「認証情報が平文で送信されるのか」が論点になる場合があります。その場合は、次のように説明できます。

    YAMAHA RTX と PIO-ID を組み合わせたリモートアクセスVPNの2要素認証では、RADIUSのPAP認証を利用します。ただし、RADIUSにおけるPAPでは、パスワードはRADIUS共有シークレットとRequest Authenticatorを用いて暗号化されます。そのため、パスワードがそのまま平文で送信されるわけではありません。

    なお、ここでいう暗号化は、RADIUSパケット全体ではなく、パスワード情報に対する暗号化です。通信全体をTLSで保護するRadSecとは異なります。
